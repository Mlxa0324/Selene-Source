# Flutter Performance Playbook

这是一份面向 Selene 的 Flutter 性能优化作战手册。

目标不是“看到卡顿再救火”，而是让你以后在开发阶段就能按统一规范把首帧、首播、滚动、焦点、图片、骨架和路由链路设计对。

---

## 1. 总原则

### 1.1 性能目标顺序

性能优化不要平均用力，按下面顺序排优先级：

1. **首帧是否尽快可见**
2. **首个可交互状态是否尽快可用**
3. **首个可播放状态是否尽快开始**
4. **滚动和焦点移动是否稳定**
5. **持续浏览时是否避免无意义重建和重复请求**
6. **装饰性动画是否克制**

判断标准：

- 用户能不能尽快“看到东西”
- 用户能不能尽快“开始操作”
- 用户能不能尽快“开始播放”
- 后续的推荐、补源、预热、动画、统计，是否都退到了后台

### 1.2 关键链路与次要链路

每个性能问题都先拆成两部分：

- **关键链路**：不完成就无法看到首屏、无法拿到首个焦点、无法起播
- **次要链路**：推荐、补源、配置预热、额外排序、图片补齐、装饰动画、轻提示

规则：

- 关键链路只能依赖关键链路
- 次要链路绝不能卡住关键链路
- 次要链路失败时，关键链路仍然要正常工作

### 1.3 先减等待，再减工作量

很多卡顿不是“算得太慢”，而是“等了不该等的东西”。

优化优先级：

1. 先检查有没有多余的 `await`
2. 再检查有没有多余的排序、过滤、集合重建
3. 再检查有没有多余的滚动、副作用动画和重绘
4. 最后才考虑更重的手段，比如额外抽象、 isolate、复杂缓存

## 2. 开工流程

### 2.1 先读仓库规范

涉及 Flutter 前端时，先读：

- `.trellis/spec/frontend/index.md`
- `.trellis/spec/guides/index.md`

涉及 TV 时，再读：

- `.trellis/spec/frontend/tv-mode.md`

### 2.2 先复现，再下刀

先把问题归类，不要一上来拍脑袋改：

- 首帧慢
- 首播慢
- 滚动掉帧
- 焦点移动发涩
- 骨架动画干扰
- 图片加载风暴
- 返回或路由链路多次触发
- 大量 rebuild

### 2.3 先写最小失败用例

优先写最小回归测试：

- widget test：页面首帧、首播、焦点、滚动、骨架、弹框
- service test：配置缓存、代理预热、数据去重

建议方式：

```bash
flutter test test/tv_app/xxx_test.dart --plain-name "精确描述问题"
```

命名要直接描述症状，例如：

- `renders detail player before ad filter preference resolves`
- `detail keeps first playable source independent from slow recommends`
- `renders fullscreen player before ad filter preference resolves`

### 2.4 先做最小闭环验证

修完后至少跑：

```bash
flutter analyze lib/tv_app
flutter test test/tv_app/目标测试文件.dart
git diff --check
```

如果改动只在单个 widget，也要优先跑对应测试，而不是只靠肉眼体感。

## 3. 性能问题快速分诊表

| 症状 | 高概率根因 | 第一修复方向 |
| --- | --- | --- |
| 详情页进去后要等很久才能播 | 推荐、配置、补源和首播绑成一条等待链 | 拆关键链路，先起播，推荐和补源后台回填 |
| 全屏播放器打开卡一下 | 初始化时读了非必要配置，或重复解析播放地址 | 预热配置，去掉空转解析，避免同地址重复下发 |
| 首页上下滚动掉帧 | 每次获焦都触发父滚动、整段重建、图片请求并发过多 | 收紧 `ensureVisible`，隔离重绘，限制滚动期图片加载 |
| 横向列表左右移动发涩 | 同一分区内也在频繁纵向滚动或 reset | 区分“分区内移动”和“跨分区进入” |
| 骨架屏一直刷 | 占位动画无限循环 | 设定最大轮次，超出后静止 |
| build 期间一直排序 | getter 或 builder 内部重复算派生数据 | 改为缓存结果，只在源数据变更时重算 |
| TV 返回异常 | 返回键链路重入，多次 pop | 做防重入锁，只放过第一次返回 |

## 4. 首帧与首播链路

### 4.1 详情页和播放器的第一原则

详情页、内嵌播放器、全屏播放器都要遵守：

- **先拿到第一份可播数据**
- **先渲染第一份可视 UI**
- **先让播放开始**
- 然后才补推荐、补源、预热、收藏态、统计态

错误示例：

- 等相关推荐回来后再结束 loading
- 等代理配置读取完成后再构建播放器
- 等所有播放源聚合完再选择第一条可播源
- 把账号配置、图片配置、弹幕配置都放进首屏 `await`

正确做法：

- 首个可播源一到就 `setState`
- 次要结果通过单独回调或独立 future 增量回填
- 预热类配置提前做、后台做、缓存做

### 4.2 首屏只保留一个“必须等待”的条件

详情页首屏通常只应等待这类条件：

- 当前视频至少有一个可播源
- 页面最小骨架或基础信息可显示

不应该阻塞首屏的条件：

- 推荐列表
- 全量源列表
- 代理地址预热结果
- 自动去广告偏好
- 图片完整加载
- 统计上报

### 4.3 异步拆分模板

推荐模板：

```dart
Future<void> loadPage() async {
  // 第一段：关键链路，只负责尽快可见/可播。
  final SearchResult? firstPlayable = await _loadFirstPlayable();
  if (!mounted) {
    return;
  }
  setState(() {
    _currentDetail = firstPlayable;
    _isInitialLoading = false;
  });

  // 第二段：次要链路，独立补齐，不影响首屏。
  unawaited(_loadRecommendations());
  unawaited(_loadRemainingSources());
  unawaited(_prewarmConfigs());
}
```

关键点：

- 首屏和次要任务分开
- 每个次要任务都能单独失败
- 任何次要任务失败，都不能把首屏打回 loading

### 4.4 增量回填优先于“一次性全等完”

如果数据来源天然支持增量返回：

- 首个匹配结果先上屏
- 后续结果再去重追加

适用场景：

- 搜索多源聚合
- 详情页补源
- 推荐补卡片
- 大列表分页加载

### 4.5 配置预热要“先缓存，再复用”

配置读取的正确姿势：

- 进入详情页时并行预热代理地址、播放偏好等轻配置
- 真正开始播放时优先复用已预热结果
- 不要在每次换源、换集、重进全屏时重复读取同一配置

不推荐：

- 每次组装播放地址都重新读 `SharedPreferences`
- 每次 build 都重新发起配置读取

## 5. 异步任务解耦

### 5.1 任务互不影响，是默认设计

一个页面内常见任务：

- 基础数据
- 首个可播内容
- 剩余数据补全
- 推荐数据
- 图片加载
- 偏好预热
- 日志统计

默认规则：

- 这些任务应该尽量独立
- 除非存在明确业务依赖，否则不要串 `await`

### 5.2 每个任务单独维护状态

不要用一个大 loading 覆盖整个页面全部任务。

更好的做法：

- `_isInitialLoading` 只管首屏
- `_isRecommendationsLoading` 只管推荐
- `_isMoreSourcesLoading` 只管补源
- `_hasPrefetchedProxy` 只管预热状态

这样好处：

- 推荐失败不会把播放器一起锁死
- 补源慢不会影响当前源播放
- 某个局部区域可以独立展示 skeleton 或空态

### 5.3 状态提交要局部、要最小

`setState` 时只改当前任务真的相关字段。

坏味道：

- 一个任务完成时顺手把别的无关区域状态也重置一遍
- 多个分支复制粘贴同一堆“清空字段”代码

推荐处理：

- 抽 `_clearSearchSession()`、`_resetSearchResults()` 这类小方法
- 让状态重置入口集中，避免漏改

### 5.4 后台任务必须可取消或可忽略

如果页面已经销毁，后台任务回调回来要安全退出：

```dart
if (!mounted) {
  return;
}
```

如果任务结果已经过期，也要主动忽略：

- 上一次搜索的慢请求晚于新搜索结果返回
- 老的详情页推荐结果晚于新的影片切换返回
- 老的播放地址解析晚于当前选中集返回

## 6. 重建与派生数据

### 6.1 build 期间不做重活

下面这些都尽量不要出现在 `build`、常用 getter、`builder` 内：

- 排序
- 去重
- 分组
- 大集合 `map/filter/fold`
- 反复构造相同列表

原因：

- 页面 rebuild 比你想象中频繁
- TV 焦点移动、动画、滚动、尺寸变化都会带来更多 build

### 6.2 派生数据要缓存

凡是满足以下条件，就应该缓存：

- 结果只依赖几个明确字段
- 该结果在页面上被反复读取
- 计算过程涉及排序、分组、去重或对象重建

典型例子：

- 线路列表按集数排序
- 当前线路置顶
- 搜索结果按某字段聚合
- 选集按分组拆分

建议模式：

```dart
void _recomputeVisibleSources() {
  _sortedSourcesCache = _buildSortedSources(_sources);
  _pinnedSourcesCache = _pinCurrentSource(
    _sortedSourcesCache,
    _currentDetail,
  );
}
```

只在这些时机重算：

- `_sources` 变了
- `_currentDetail` 变了

不要在 getter 里每次读取都重新算。

### 6.3 大组件只刷新真的变化部分

如果一个页面有多个独立区块：

- 播放器区
- 元信息区
- 选集区
- 推荐区
- 设置区

尽量避免一个区块的小变动把整页都刷一遍。

可选手段：

- 局部拆 Widget
- 明确区分不同 loading flag
- 局部 `ValueListenableBuilder`
- 仅在必要时才 `setState`

### 6.4 先减“重复计算”，再谈“状态管理升级”

很多 Flutter 页面卡顿，并不是缺少某个状态管理库，而是：

- getter 里反复排序
- 每次焦点变化整页重算
- 每次滚动都触发多余动画

先把这些基础问题清掉，再考虑更重的架构调整。

## 7. 滚动、焦点与列表

### 7.1 TV 页面最容易卡在“焦点引发额外滚动”

TV 场景里最常见的卡顿源头不是手指滚动，而是：

- 焦点每移动一次，就触发父列表滚动
- 焦点在同一横排左右移动，也触发纵向 `ensureVisible`
- 明明目标 offset 没变，还在反复 `animateTo`

### 7.2 只在“真正需要”时滚动

`ensureVisible` 要遵守：

- 焦点进入一个新分区时，再考虑纵向对齐
- 同一分区内左右移动，不要每次都滚父级
- 目标 offset 基本没变化时，直接跳过 `animateTo`

实战规则：

- **同分区内移动**：优先保持当前纵向位置稳定
- **跨分区进入**：再做一次温和对齐

### 7.3 分区进入和分区内部移动要分开处理

首页横向分区建议：

- 从其它分区进入当前分区时，允许父级纵向滚动
- 当前分区内左右切换卡片时，只做横向浏览，不要重复触发纵向动画
- 离开分区后，如需求要求复位，再恢复到最左项

### 7.4 跳过无意义滚动

如果目标滚动位置和当前几乎一致：

- 直接不滚
- 不要为了“形式上调用过”而强行 `animateTo`

这类小优化对 TV 很值：

- 少一次动画
- 少一次合成层更新
- 少一次感知上的“发涩”

### 7.5 首尾安全留白要兼容获焦放大

TV 卡片获焦会放大，所以：

- 首列和末列要预留安全边距
- 最右列获焦时可改为向内放大
- 不要让焦点边框被裁切

### 7.6 长列表必须控制一次性工作量

对大 Grid 或大列表：

- 首批先只开放一部分卡片参与构建和焦点导航
- 焦点逼近尾部时，再逐批放开
- 图片请求也跟着滚动节奏延后

这样做能显著降低：

- 首次布局压力
- 初始图片并发
- 焦点计算开销

## 8. 占位动画与图片加载

### 8.1 骨架动画是提示，不是常驻演出

骨架屏的职责：

- 告诉用户“这里有内容正在来”

骨架屏不该做的事：

- 无限循环抢注意力
- 图片迟迟不来时一直刷个不停

规则：

- 骨架动画限制最大轮次
- 到达轮次上限后，保留静态占位即可

### 8.2 雨刷动画要有上限

推荐策略：

- 初始只刷 2 次
- 图片如果仍未回来，就静态停住

这样能避免：

- 页面多个 skeleton 一起持续运动
- GPU 和合成压力上升
- 用户注意力被骨架吸走

### 8.3 快速滚动时延后真实图片请求

当列表快速滚动时：

- 先显示骨架
- 等滚动趋稳后再开始真实网络图片加载

适用场景：

- 首页横向大卡片
- 搜索结果
- 纵向 Grid
- 推荐区横向卡片

不要做的事：

- 滚动经过一大排卡片就立刻全发图片请求
- 滚动中反复取消又重开同一批图片加载

### 8.4 图片加载触发要尽量“一次到位”

卡片进入可加载状态后：

- 只触发一次真实图片构建
- 不要因为小范围 rebuild 又回退到初始骨架态

### 8.5 网络慢时要接受“先没有图”

性能优化的目标不是“保证图片一定马上来”，而是：

- 即使图片慢，也不拖累浏览和操作

所以如果图片慢：

- 卡片应继续可聚焦、可浏览
- skeleton 到轮次上限后静止
- 不要让整个页面因为图片而持续动个不停

## 9. RepaintBoundary 与绘制隔离

### 9.1 什么时候加 `RepaintBoundary`

适合加在这些位置：

- 首页整段横向分区
- 播放器上方的复杂可复用装饰区
- 包含图片、阴影、边框和动画的重卡片区域

判断标准：

- 这个区域本身内容相对稳定
- 外部父级会频繁滚动、重建或动画
- 你希望隔离重绘影响

### 9.2 不要滥加

`RepaintBoundary` 不是越多越好。

只在这些场景加：

- 区块级内容可独立重绘
- 确实存在父级频繁刷新拖累子级的问题

## 10. 路由、返回和页面切换

### 10.1 路由打开也属于性能体验

如果一个页面跳转后：

- 先黑一下
- 先卡一下
- 或者回来时多 pop 一次

用户体感上依然是“卡”。

### 10.2 返回链路要防重入

TV 遥控器下，返回键很容易出现：

- 长按重复触发
- 同一条返回链路里连续收到多次事件

规则：

- 返回只响应第一次按下
- 当前返回流程结束前，不要释放锁
- `KeyRepeatEvent` 和 `KeyUpEvent` 不得重复执行业务 pop

### 10.3 页面跳转包装要统一

如果 TV 页面跳转都有：

- `PageRouteBuilder`
- `TvTheme.wrapScope`
- `Duration.zero`

就应该抽统一路由方法，避免：

- 某一条跳转忘包主题
- 某一条跳转动画不一致
- 某一条跳转多做一层 build

这类优化收益更多在维护性，但维护性越稳，后面越不容易引入性能回退。

## 11. 设置页、弹窗和轻交互

### 11.1 设置提交要减少重复动作

设置页常见问题：

- 扫码回填后还要手动保存一遍
- 保存时多个配置分散提交
- 多个分支手动清同一堆状态

建议：

- 能一次自动保存的，就不要让用户多确认一次
- 一次提交里把同一业务域的配置一起落盘
- 保存成功后给轻量反馈，不要上重弹窗或复杂动画

### 11.2 反馈弹窗要轻

轻提示弹窗建议：

- 半透黑背景
- 无边框
- 高度偏矮
- 存在时间短

这类调整更多是体验优化，但也能减少视觉噪音和不必要绘制。

## 12. 代码味道清单

看到这些味道，要优先警觉：

- getter 里排序、过滤、去重、重建列表
- `initState` 里串了一长串互不依赖的 `await`
- 推荐、补源、配置预热全绑在同一个 loading 上
- 同一组状态字段在多个分支里手动清空
- 焦点左右移动时也在反复滚父容器
- `ensureVisible` 每次都 `animateTo`
- skeleton 无限循环
- 大量图片在快速滚动时同时开始请求
- 同一个播放地址被重复解析、重复下发
- 空回调留着不删，让人误以为后面还有业务

## 13. TV 专项规则

### 13.1 TV 不是普通移动端放大版

TV 性能问题比手机更容易暴露，因为：

- 焦点移动频率高
- 页面常有多个横向区块
- 大屏上一屏可见卡片更多
- 用户对“方向键一按就有响应”非常敏感

### 13.2 TV 页面重点看三件事

1. 焦点移动时有没有多余滚动
2. 首屏卡片和图片是否并发过猛
3. 播放器是否被次要任务阻塞

### 13.3 TV 页面默认检查项

每次改 TV 页面，默认检查：

- 焦点进入、离开、确认键行为是否清晰
- 同分区移动是否仍保持纵向稳定
- 横向分区离开后是否按需求复位
- 返回键是否只触发一次
- 骨架动画是否有限次
- 图片滚动加载是否节流
- 首帧是否不等推荐
- 首播是否不等配置预热

---

## 14. 跨端隔离与回归

### 14.1 改 TV 时，默认假设会波及手机端

因为很多逻辑会复用：

- 搜索状态
- 播放记录
- 配置服务
- 路由返回
- 图片代理

规则：

- 改 TV 专属行为，优先收敛在 `lib/tv_app/`
- 如果动到了跨端服务或公共状态，就补手机端/普通端回归验证

### 14.2 不要把“局部优化”写成“全局副作用”

例如：

- 只为 TV 搜索页清状态，却改了公共搜索服务全局行为
- 只想优化 TV 返回，却改坏了手机端导航

优先策略：

- TV 特有逻辑放 TV 层
- 跨端公共逻辑改动前先确认影响面

## 15. 推荐验证矩阵

### 15.1 代码验证

至少执行：

```bash
flutter analyze lib/tv_app
git diff --check
```

如果是局部改动，也可以更聚焦：

```bash
flutter analyze lib/tv_app/widgets/tv_home_section.dart
flutter analyze lib/tv_app/widgets/tv_focus_scroll.dart
```

### 15.2 测试验证

按问题类型补回归：

- 首帧/首播：widget test，验证页面是否在次要任务未完成前已可见/可播
- 焦点/滚动：widget test，验证方向键行为和滚动触发边界
- 骨架/图片：widget test，验证雨刷上限和延迟加载
- 设置/弹窗：widget test，验证自动保存和轻反馈样式

### 15.3 体感验证

真机或模拟器手动关注：

- 进入详情页，播放器是否更早出现
- 进入全屏，是否少了一次明显等待
- 首页上下切分区时，是否少了“整段跟着抖一下”
- 横向列表左右快速移动时，纵向是否稳定
- 图片慢时，页面是否仍然安静、可操作

## 16. 实战落地点

本仓库已经验证过、值得复用的优化方向：

- `lib/tv_app/screens/tv_video_detail_screen.dart`
  - 首个可播源先起播，推荐和补源后台回填
- `lib/tv_app/screens/tv_fullscreen_player_screen.dart`
  - 播放器初始化不再等待次要配置
- `lib/tv_app/widgets/tv_video_card.dart`
  - 骨架雨刷只刷有限次数，滚动期延后图片请求
- `lib/tv_app/widgets/tv_home_section.dart`
  - 同分区左右移动不再每次都触发父级纵向滚动
- `lib/tv_app/widgets/tv_focus_scroll.dart`
  - 目标 offset 几乎不变时跳过滚动动画

以后碰到类似问题，优先复用这些思路，而不是重新发明一套。

## 17. 不要过早使用的“重手段”

在下面这些基础问题没清掉前，不要急着上重方案：

- isolate
- 复杂全局缓存
- 大规模状态管理重构
- 组件树大拆重写
- 过度抽象的性能框架

先清：

- 无关等待
- 重复排序
- 重复滚动
- 无限动画
- 图片并发风暴

很多时候，这些基础问题清掉以后，体感已经能明显改善。

## 18. 每次优化结束时的交付格式

每次完成优化，输出内容至少包括：

1. 问题属于哪一类
2. 原始关键阻塞点是什么
3. 关键链路和次要链路怎么拆的
4. 改动点落在哪些文件
5. 跑了哪些验证命令
6. 还有哪些风险没彻底消掉

这样下一次再回来，不需要重新推理一遍。

---

## 19. 一句话判断这次优化有没有做对

如果你的改动满足下面四条，通常方向就对了：

1. 用户更早看到内容
2. 用户更早开始操作或播放
3. 页面在滚动和焦点移动时更安静
4. 次要任务失败时，主流程仍然稳定

如果只是把工作挪到了别的地方，却没有减少等待、减少重建或减少副作用，那大概率还不算真正优化。
