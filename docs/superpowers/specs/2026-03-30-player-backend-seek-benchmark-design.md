# 播放器后端 Seek Benchmark 隐藏实验页设计

**日期：** 2026-03-30

## 目标

在项目内新增一个隐藏的播放器 benchmark 实验页，用同一条 HLS 测试源、同一组左向 seek 场景，对比 4 套播放后端的 seek 表现：

1. `WebView`
2. `video_player`
3. `media_kit`
4. `fvp`

实验页的目标不是替换正式播放器，而是给真机对比提供统一、可重复的数据，重点回答：

- 哪个后端的 `seek` API 返回更快
- 哪个后端的目标位置稳定更快
- 哪个后端的转圈/缓冲时间更短
- 哪个后端的 seek 精度更接近目标位置

## 范围

- `lib/widgets/user_menu.dart`
- 新增隐藏 benchmark 页面及其配套组件/模型
- 新增 benchmark 用播放后端驱动抽象
- 新增 `WebView / video_player / media_kit / fvp` 对应的 benchmark 驱动
- `pubspec.yaml` 中补充 `fvp` 依赖
- 与 benchmark 逻辑直接相关的测试

## 非目标

- 不改正式播放页 `PlayerScreen` 的业务逻辑
- 不把 `fvp` 接入正式播放器链路
- 不把弹幕、选集、定时关闭、投屏、PiP 等业务能力带进 benchmark
- 不在本次工作中对四个后端做 seek 优化，只做测量和对比
- 不追求一键全自动端到端测速，真机页面人工触发即可

## 入口设计

实验页采用隐藏入口，避免干扰正常用户路径：

- 打开 `用户菜单`
- 进入 `应用设置`
- 长按版本号区域，进入隐藏 benchmark 页面

页面内部提供显式后端切换：

- `WebView`
- `video_player`
- `media_kit`
- `fvp`

## 页面结构

隐藏实验页采用单页实验台布局，确保同一设备上切换后端足够快：

1. 顶部后端切换栏
   - 四个分段选项：`WebView / video_player / media_kit / fvp`
2. HLS 测试源区域
   - 一个 URL 输入框
   - 一个“恢复默认测试源”按钮
   - 第一版默认只内置一条统一测试源
3. 播放器预览区域
   - 只保留最小播放能力，用于加载、播放、seek
   - 不接入弹幕、业务控制面板、选集等逻辑
4. 用例执行区域
   - `Run Warm`
   - `Run Cold`
   - `Clear Results`
   - 可视化展示预设 seek 场景：`左跳 10s / 30s / 90s / 180s`
5. 结果区域
   - 单次结果明细
   - 每组平均值、最小值、最大值

## 为什么不复用正式播放器页

正式播放器页已经叠加了弹幕、PiP、定时器、控制层、播放状态同步等逻辑。直接把 benchmark 嵌入 `PlayerScreen` 会引入额外变量，导致：

- 缓冲/转圈时间被业务逻辑污染
- seek 数据掺杂弹幕与控制层联动开销
- 真机对比时难以确认问题到底来自后端还是业务层

因此 benchmark 页需要单独实现一套很薄的实验层，只复用必要的播放器基础能力。

## 后端抽象设计

新增一个只面向 benchmark 的轻量抽象，例如 `BenchmarkPlayerDriver`，统一约束四个后端：

- `load(String url)`
- `play()`
- `pause()`
- `seek(Duration position)`
- `dispose()`
- 当前 `position`
- 当前 `buffering`
- 可播放/已就绪信号

页面只依赖这个抽象，不直接感知底层实现细节。

### 各后端接入策略

#### WebView

复用现有 `WebView` 路线的核心能力，重点保留已有 `fastSeekTo`、缓冲/时间事件监听，确保它作为现有性能基线参与对比。

#### video_player

使用 Flutter 官方 `video_player`，作为原生基线实现。

#### media_kit

使用当前项目已有 `media_kit` 能力，作为跨平台高性能内核样本。

#### fvp

`fvp` 仅接入 benchmark 页面，不先接进正式播放链路。这样可以先验证其 seek 数据是否值得后续投入正式播放器改造。

## 测量口径

每次 seek 统一记录 4 个时间点：

- `t0`：发起 seek 的时刻
- `t1`：seek API 返回的时刻
- `t2`：播放器位置第一次稳定到目标附近的时刻
- `t3`：buffering 结束且播放恢复推进的时刻

对应输出 4 个指标：

- `api_return_ms = t1 - t0`
- `position_settle_ms = t2 - t0`
- `buffering_clear_ms = t3 - t0`
- `delta_ms = 实际位置与目标位置误差`

### 判定规则

为保证四个后端结果可比，统一采用以下判定：

- “位置稳定”定义为：当前位置进入目标时间 `±500ms` 区间，并连续保持至少 `200ms`
- “buffering 结束”定义为：buffering 从 `true` 回到 `false`，并且当前位置重新开始推进
- 单次 seek 的最大等待时间统一为 `15s`
- 若某个阶段超时，则该次结果标记为超时/失败，并保留已采样到的中间数据

## 测试流程

### 场景锚点

为保证“左向 seek”在四个后端上可重复，所有预设场景都基于同一个锚点位置执行：

- 默认锚点位置：`240s`
- 四个左跳场景分别为：
  - `240s -> 230s`（左跳 `10s`）
  - `240s -> 210s`（左跳 `30s`）
  - `240s -> 150s`（左跳 `90s`）
  - `240s -> 60s`（左跳 `180s`）

默认测试源必须足够长，至少覆盖 `240s` 锚点和全部左跳目标位置。

### Warm 测试

同一播放器实例、同一视频连续执行：

- 先把播放器稳定到锚点 `240s`
- 再执行四组左跳场景
- 每次执行下一组场景前，都重新回到锚点 `240s` 并等待稳定

每个场景执行 5 次。

### Cold 测试

每次 seek 场景前重建播放器实例并重新加载视频，然后：

- 播放器加载完成
- 定位到锚点 `240s` 并等待稳定
- 执行对应左跳场景

每个场景执行 5 次。

### 结果输出

每组数据需要同时展示：

- 单次明细
- 平均值
- 最小值
- 最大值

## 默认测试源策略

第一版 benchmark 默认只使用一条统一 HLS 测试源，以减少变量并提高不同后端之间的可比性。

页面仍保留 URL 输入能力，用于后续人工替换测试流。但默认场景下，所有后端都先跑同一条内置测试源。

## 状态与结果模型

建议单独定义 benchmark 结果模型，避免页面直接拼装临时 Map：

- 后端类型
- 测试模式（`warm` / `cold`）
- seek 场景（`10s / 30s / 90s / 180s`）
- 第几次执行
- 目标位置
- `api_return_ms`
- `position_settle_ms`
- `buffering_clear_ms`
- `delta_ms`
- 状态（成功 / 超时 / 失败）
- 错误信息（如有）

## 风险

- `fvp` 为新增依赖，可能带来平台集成问题，需要先验证 Android/iOS 能正常编译和初始化
- 四个后端暴露的 buffering/ready 信号粒度不同，统一判定时需要做轻量归一化
- HLS 测试源本身的网络波动会影响结果，因此 benchmark 数据是“当前网络环境下的真实表现”，不是绝对值
- 若复用现有 WebView 路线时带入额外优化配置，需明确它代表“项目当前最佳 WebView 基线”，而不是裸 WebView

## 验证

- 为 benchmark 结果采集逻辑添加测试，覆盖：
  - `api_return_ms` 记录正确
  - 位置稳定判定正确
  - buffering 结束判定正确
  - 超时结果能正确标记
- 为页面交互添加基础测试，覆盖：
  - 后端切换
  - 结果清空
  - 测试按钮触发对应流程
- 运行受影响测试、`dart format`
- 在条件允许时运行 `dart analyze`

## 验收标准

- 四个后端都能在隐藏 benchmark 页中加载并执行 seek
- 每次 seek 都能记录统一的 4 项指标
- `Run Warm` 与 `Run Cold` 都能产出结果
- 结果列表可重复使用，不因切换后端或重复执行而串数据
- 隐藏入口稳定可用，正常用户路径不暴露该实验页
