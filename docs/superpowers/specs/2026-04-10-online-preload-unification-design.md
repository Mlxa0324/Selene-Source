# 在线播放预加载统一设计

**日期：** 2026-04-10

## 背景

当前播放器的“预加载”行为只在 macOS `media_kit` 链路里有显式开关，移动端和 Windows 在线播放主要走 `WebView`，没有统一的产品语义。

用户这次希望把在线播放预加载统一成同一套规则：

- 应用设置里提供统一的“预加载”开关，默认开启
- 只对在线播放生效，本地离线不做
- 预加载目标始终是当前位置右侧 5 分钟
- 进度条显示浅色缓存范围
- 向左拖动时，如果之前已经实际缓过，就应该命中缓存
- 但不能把“理论上应该已经预读到的未来内容”误判成左拖一定可复用缓存

这意味着本次需求的重点不是单纯“多拉一点数据”，而是把“预加载”“已确认缓存”“左拖命中”的语义统一并可视化。

## 目标

- 全平台统一提供一个“预加载”应用设置，默认开启
- 统一只作用于在线播放：
  - Android `WebView`
  - iOS `WebView`
  - Windows `WebView`
  - macOS `media_kit`
- 本地离线播放完全不受影响
- 在线播放时，始终尽量补齐当前位置右侧 5 分钟的预加载窗口
- 进度条浅色区域显示“已确认缓存的整段范围”
- 左拖时只根据“已确认缓存区间”判断是否应命中缓存，避免错误复用未来预读假象

## 非目标

- 不改本地离线视频播放链路
- 不重做现有播放器后端选型
- 不把缓存落盘成真正的离线下载能力
- 不承诺所有平台都能 100% 精确缓存到刚好 5 分钟；目标是统一“尽量补齐右侧 5 分钟”的产品行为和命中判断

## 方案对比

### 方案 A：统一维护“已确认缓存区间”，并持续补右侧 5 分钟窗口

做法：

- 设置层引入统一预加载开关
- 各在线播放后端维护“已确认缓存区间”
- 主动预加载只负责尽量补右侧 5 分钟
- UI 和 seek 判断都只认“已确认缓存区间”

优点：

- 最符合用户对产品语义的要求
- 可以同时满足“右侧持续预加载”和“左拖命中已缓过内容”
- 能规避把未来理论缓存误判成已命中缓存

缺点：

- 需要同时修改设置、播放器状态同步、WebView 预加载逻辑和进度条展示
- `WebView` 与 `media_kit` 的底层能力不同，需要分别接入但统一抽象

### 方案 B：只展示底层播放器天然 `buffered` 范围，不显式维护统一缓存语义

优点：

- 改动较小

缺点：

- 很难稳定表达“右侧 5 分钟预加载”
- 无法可靠区分“已确认缓存”和“理论预读目标”
- 左拖命中语义会继续依赖平台底层表现，容易延续现有歧义

### 方案 C：为预加载单独开隐藏播放器实例

优点：

- 预加载状态和主播放器理论上隔离最清晰

缺点：

- 实现和资源成本都明显偏高
- 移动端和平板端风险较大
- 不适合作为当前需求的首选

## 推荐方案

采用方案 A。

也就是：

- 用统一设置控制全平台在线播放预加载
- 用统一的“已确认缓存区间”表达实际可复用缓存
- 用“当前位置右侧 5 分钟窗口”表达主动预加载目标
- 用浅色进度条展示已确认缓存，而不是展示理论预加载计划

这样既能满足“从 0 分钟看到 10 分钟后，左拖回 3 分钟应该走缓存”，也能避免继续出现“未来预读看起来像缓存、实际左拖又不中”的体验问题。

## 详细设计

### 1. 应用设置统一成一个全平台预加载开关

在应用设置中新增统一的“预加载”选项，使用横向单选形式展示“开 / 关”，默认值为“开”。

要求：

- 设置项在全平台都可见
- 文案不再限定 `media_kit`
- 持久化使用新的统一 key，而不是只保留 macOS 专用命名
- `PlayerScreen` 加载该设置后，下发给 `VideoPlayerWidget`

兼容策略：

- 若新 key 尚无值，可优先回退旧的 `media_kit` 预加载配置，避免 macOS 老用户升级后体验突变
- 一旦用户显式切换新开关，后续统一以新 key 为准

### 2. 统一“预加载目标”和“已确认缓存”两个概念

本次设计明确区分两个状态：

- 预加载目标窗口：当前位置右侧 5 分钟，表示系统希望尽量补齐的范围
- 已确认缓存区间：播放器或预加载请求已经实际拿到的数据范围，表示 UI 可展示、seek 可依赖的范围

关键原则：

- UI 只展示已确认缓存区间
- 左拖命中判断只依赖已确认缓存区间
- 不能把“理论上应该缓到了”直接当成“已经可复用缓存”

### 3. WebView 链路：以片段级确认结果汇总缓存区间

对 Android、iOS、Windows 的 `WebViewPlayerAdapter`：

- 继续复用现有 `hls.js`/WebView 播放链路
- 增加预加载状态管理器，用于记录：
  - 当前目标预加载窗口
  - 已确认缓存区间集合
  - 最近一次 seek 后围绕新位置重建的窗口版本

已确认缓存来源：

- 正常播放过程中，播放器实际成功加载并消费过的片段
- 主动预加载请求成功拿到的片段

区间维护原则：

- 按照片段对应时间范围合并为区间集合
- 相邻或重叠区间自动合并
- seek 到新位置后，右侧 5 分钟目标窗口更新，但旧的已确认缓存区间不因“位置变化”被逻辑上强制清空
- 只有在底层实际确认缓存失效，或媒体源切换、集数切换、URL 切换时，才整体重置区间集合

### 4. macOS `media_kit`：保留底层能力，统一上层语义

对 macOS `media_kit`：

- 保留现有更大 `bufferSize` 的预加载思路
- 不强行复刻 WebView 的片段预取实现
- 上层仍统一成“已确认缓存区间”的展示和判断语义

具体做法：

- 继续读取 `media_kit` 可提供的 buffer/position/duration 状态
- 将其转换为统一缓存区间表示，供进度条展示与交互逻辑使用
- 不把 buffer 理论外推成更多可复用范围

这样可以保留 macOS 现有底层优势，同时避免 UI 层和用户心智继续分裂。

### 5. 左拖与右拖的 seek 规则

#### 左拖

- 若目标时间落在已确认缓存区间内，则按“应命中缓存”处理
- 若目标时间不在已确认缓存区间内，则允许底层重新拉流
- 不允许因为“右侧有一个理论 5 分钟窗口”就推断左拖一定命中

#### 右拖

- seek 到新位置后，立即把预加载目标窗口移动到“新位置右侧 5 分钟”
- 如果旧位置附近已有已确认缓存区间，保留其实际已确认部分，不做逻辑层硬清空
- 新窗口内只有真正确认到的数据才会进入浅色缓存展示

### 6. 进度条浅色缓存展示

浅色进度条统一展示“已确认缓存的整段范围”，而不是“计划预加载窗口”。

这样表现为：

- 正常连续观看时，浅色范围会从左到右逐步扩展
- 如果右侧主动预加载成功，浅色范围也会继续往前延伸
- 当用户左拖时，如果目标落在浅色区域内，用户的视觉预期与实际命中更一致

对于多段缓存的情况：

- 若当前进度条组件支持多段显示，则直接显示多个浅色区段
- 若当前组件只支持单段显示，则先实现“包含当前位置的主缓存段”展示
- 该限制需要在实现阶段结合现有控件结构选择最小改动方案，但语义仍保持“展示已确认缓存”

### 7. 关闭预加载时的行为

预加载关闭后：

- 不再主动补当前位置右侧 5 分钟
- 已确认缓存区间仍可反映底层自然产生的缓存，但不再承诺额外前向预加载行为
- UI 上可以继续展示底层实际已确认缓存，也可以只在存在实际缓存时显示浅色条；实现时选择对现有控件改动更小的方案

重点是：

- “关闭”只关闭主动预加载
- 不要求人为抹掉播放器底层已经自然持有的缓存

## 数据与接口调整

建议新增或调整以下接口：

- `UserDataService`
  - 新增统一预加载配置 key
  - 新增统一读写方法，如 `savePlaybackPreloadEnabled(...)` / `getPlaybackPreloadEnabled(...)`
  - 保留对旧 `media_kit` 配置的兼容回退
- `PlayerScreen`
  - 使用统一预加载配置替代仅 macOS 配置
- `VideoPlayerWidget`
  - 使用统一的 `playbackPreloadEnabled` 参数
  - 将该参数传给 `WebViewPlayerAdapter` 与 macOS `media_kit` 分支
- `PlayerAdapter` / 具体 adapter
  - 增加统一的缓存区间读取能力，供控件层绘制浅色进度条

## 测试策略

### 单元测试

- 缓存区间合并逻辑：
  - 重叠区间合并
  - 相邻区间合并
  - 多段区间保留
- 统一配置读取逻辑：
  - 新 key 命中
  - 新 key 缺失时回退旧 key

### Widget / 逻辑测试

- 预加载开启时，`PlayerScreen` 会把统一开关正确下发到播放器
- 预加载关闭时，不触发主动补右侧 5 分钟逻辑
- 进度条浅色区域根据“已确认缓存区间”更新，而不是直接根据理论窗口更新

### 回归场景

- 从 0 分钟连续播放到 10 分钟，再左拖到 3 分钟，应优先命中已确认缓存
- 在 10 分钟处右拖到 25 分钟，右侧 5 分钟窗口围绕新位置重建
- 切换集数、换源、切换 URL 时，旧缓存区间重置
- 本地离线视频链路无行为变化
- macOS、Windows、Android、iOS 在线播放的设置语义一致

## 风险

- 不同平台底层播放器对“缓存已确认”的可观测粒度不同，统一抽象时需要接受一定的精度差异
- 如果现有进度条组件不支持多段缓存展示，第一版可能需要先展示“主缓存段”，后续再扩展完整多段可视化
- WebView 预加载如果过于激进，可能带来额外流量和内存压力，因此需要严格限制在“当前位置右侧 5 分钟”和受控并发内
